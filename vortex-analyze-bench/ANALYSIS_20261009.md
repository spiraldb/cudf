# Fresh CPU/GPU analysis — 2026-10-09

## Bottom line

One new Q5 capture, **no optimization/source changes or new benchmark comparison**.

1. **The input barrier is real and lineitem finishes last.** Reading, decoding, importing and materializing all six tables occupies 25.719 ms of this instrumented 33.282 ms API timer bracket. Relational Q5 begins only after every table future is joined.
2. **Millisecond waits are not millisecond OS runnable delays here.** Raw ftrace resolves what the old `Unknown` scheduling states could not: read-thread wake-to-run median 1.248 µs, p95 2.112 µs, maximum 12.928 µs. Most off-CPU time precedes wakeup, inside blocking paths.
3. **The largest 2.166 ms GPU no-recorded-work interval is not simply a late submitter.** Its ending copy API returned 2.019 ms before the copy ran. Matched event dependencies do not explain that long tail.
4. **That largest spike is strongly contaminated by instrumentation.** A driver-side thread that wakes the application has an explicitly recorded 1.679 ms `TLS allocation` profiler-overhead interval; H2D starts 8.096 µs after it ends. This is concrete interference evidence, not proof that all 2.166 ms is caused by that interval.
5. **There are smaller input/producer stalls on the lineitem tail.** We can now follow a file-read worker waking a parked consumer, followed by an H2D submission. Exact request→future→transfer identity is still absent.

**Do not optimize the 2 ms spike as though it were ordinary execution time. Do not repeat blind yield/lock experiments.** The next measurement should first separate steady-state application behavior from profiler initialization/interference. No further capture or code change has been started.

## 1. Whole-query path and timing

Source establishes this order:

```text
six parallel table-read callers
    ↓
shared async executor → blocking I/O pool → pinned file reads
    ↓
transfer submission and source retention → copy stream 29
    ↓
GPU decoders on streams 30–33
    ↓
Arrow import → cuDF materialization on stream 7 → synchronization / release
    ↓
join all six table futures
    ↓
Q5 filters → joins → arithmetic → groupby → orderby
```

Source anchors:
- `cpp/benchmarks/ndsh/local_io.hpp:104–136`: one `std::async` caller per table, then `future.get()` for all tables.
- `cpp/benchmarks/ndsh/q05.cpp:138–148`: `read_inputs()` returns before relational `execute_q5` starts.
- `cpp/benchmarks/ndsh/vortex/vortex_io.cpp:242–303`: drain `get_next`, Arrow-device import, table copy/concatenation, consumer synchronization, batch release, another drain.
- Vortex `vortex-cuda/src/pooled_read_at/file.rs:164–236`: file read on blocking pool; H2D submitted synchronously as read results are polled. Large logical reads assemble multiple chunks before returning.
- Vortex `vortex-io/src/runtime/current.rs`: caller-driven shared executor; **caller TID is not task/input ownership**.

## 2. Exhaustive read-gap accounting, not just the biggest gaps

The union of **all streams' 197 kernels, 317 copies, and 33 memsets** yields 237 maximal gaps inside the read envelope. Event markers, host callbacks, allocation/free internals and waits are not kernel/copy/memset work and may still be active during these intervals. Busy union is not SM occupancy.

Each gap is split at submission-API endpoints. The following classes look at **any subsequently recorded GPU operation**, with returned API taking precedence over in-progress API, then not-entered. They partition the 15.717792 ms exactly:

| Observable submission state during no-recorded-work intervals | Union ms | Share of read no-work time |
|---|---:|---:|
| No API for any subsequently recorded operation has been entered | 8.709024 | 55.41% |
| At least one such API is in progress, none has returned | 4.075008 | 25.93% |
| At least one such API has already returned | 2.933760 | 18.67% |

These are **submission-status observations, not root-cause or recoverable-time categories**. The already-returned operation need not be the next operation to run. Looking only at the actual next operation gives 9.314336 / 3.651392 / 2.752064 ms respectively. Incomplete capture can affect either classification.

The raw endpoint sweep independently agrees with union accounting and each window's busy+no-work duration. Different table/read/decoder windows overlap; do not sum them.

## 3. What raw scheduler events resolve

Old `SCHED_EVENTS` state fields were Unknown. New raw ftrace supplies actual switch-out state and wakeup targets. Across each of the six callers' **own** `vortex.read` range:

| State | Summed thread-time ms |
|---|---:|
| Scheduled on-CPU | 41.439947 |
| S-state switch-out → wakeup | 54.545011 |
| D-state switch-out → wakeup | 0.319106 |
| Wakeup → running | 1.223584 |
| Total across overlapping callers | 97.527648 |

903 complete wake/run cycles: **median 1.248 µs, p95 2.112 µs, p99 3.456 µs, max 12.928 µs**. Raw states: 886 S, 17 D, no R/R+ switch-outs in these windows. State partitions cover every nanosecond of the six ranges; wake-cycle sums agree with runnable intervals.

S/D→wakeup includes wake activation, not just sleep: 872 cycles have explicit `waking→wakeup` brackets totaling 4.723327 ms of thread-time. Do not include this in wakeup→run, or infer missing brackets. This does not rule out async task scheduling delays or kernel wake-path costs; it does reject a millisecond **runnable-but-denied-a-CPU** explanation for these observed waits.

Observed blocking paths include CUDA driver rwlocks, Rust executor parking, pinned retention and blocking-pool state locking. OSRT totals are summed/overlapping API times, not wall-time savings. Exact mutex owners remain unknown without lock identity/acquire/release evidence.

## 4. Concrete lineitem-tail completion chain

Global no-work gap **47.567904–47.863200 ms (0.295296 ms)**:

|---|---:|

| Worker 560991 begins waking caller 561013 | 47.747503 |

| 8 MiB H2D starts on stream 29 | 47.863200 |

Wakeup→run is **2.208 µs**, not the 0.295 ms gap. This is strong completion/wakeup association, but **not a proven identity join between that pread and that copy**.

Another gap, **48.365472–48.661088 ms (0.295616 ms)**, includes an executor park followed by `RawMutex::lock_slow → SmolExecutor::spawn_blocking_io`. Its two runnable delays are 1.984 and 2.464 µs; the caller is on-CPU for 148.753 µs within the gap. Twenty-one lineitem 8 MiB preads complete in this window, so timestamp/size matching cannot select the required input.

The early **29.142784–29.917984 ms (0.775200 ms)** gap includes pinned-retention waiters and blocking-pool `pthread_create` calls on another caller (29.415488–29.753792 and 29.770560–30.193600). Source `vortex-io/src/runtime/blocking_pool.rs` creates workers while holding its state mutex; worker keep-alive is 500 ms. This is an observed execution path, **not yet an ordinary-run bottleneck or permission to change the pool**.

## 5. Largest gap: queued work and profiler interference

**30.783328–32.949152 ms: 2.165824 ms without recorded GPU work.**

- Previous stream-29 copy c7716 finishes at 30.783328.
- Gap-ending 8 MiB H2D c7744 API: **30.860032–30.929824**, caller 561015; GPU starts **32.949152**. Most of this gap is after API return.
- Its matched stream wait references event **2120/43** (event ID / generation), complete at **30.787936**. Other immediate waits have generation zero: no valid producer match. A nearby compute-retirement wait targets an already-complete event and is submitted after c7744; it cannot explain this earlier copy's long delay.
- Meanwhile lineitem caller 561013 spends **31.303872–33.272000** inside `cuMemcpyDtoHAsync_v2` c7835 for **19 bytes**. Three CPU samples identify `copy_to_host_sync → FSST deserialize`. The 19-byte device copy actually executes **33.255904–33.258432**, after several queued H2Ds. **The long host API is not 1.97 ms of copying 19 bytes.**

The new callback/profiler-side evidence:

| Observation | Time ms |
|---|---:|
| First metadata D2H (152 bytes) finishes | 30.598176 |
| `cuLaunchHostFunc` c7713 API (registration, not callback execution) | 30.662976–30.897568 |
| Caller 561013 parks waiting for callback result | 30.899584–31.287616 |
| Driver-side worker 560896 wakes caller 561013 | 31.257935 |
| **Profiler-marked `TLS allocation` on worker 560896** | **31.262144–32.941056** |
| Caller 561013 resumes; then enters second D2H | 31.272880; 31.303872 |
| Queued H2D c7744 starts | **32.949152** |

The marked overhead duration is **1.678912 ms**, ending **8.096 µs before H2D resumes**. The worker also spends much of it switched out and later interacts with the `[NSys]` thread. There are no CPU samples or callback-body callchains on that worker, and no callback-ID→c7713 execution association. Therefore:

- Strong evidence the first callback notification reached the application before the gap ended.
- Not proof the callback had returned to CUDA or that the stream had been released.
- Not evidence for unconditional receiver rendezvous: source uses a capacity-one channel.
- **Concrete instrumentation-interference candidate, not a proven full causal explanation.**

Across all threads, explicit profiler-overhead intervals overlap 2.157728 ms of this gap. That larger union is only overlap, not additional causal evidence or subtractable overhead. For comparison, the old capture's 1.330560 ms queued-copy gap also overlaps profiler overhead throughout; its 1.900064 ms producer gap overlaps 0.653536 ms. These overlaps do not retroactively prove why earlier attempts failed, but make profile-derived speedup expectations especially unsafe.

## 6. What event completions newly establish

All **938 recorded CUDA events now have completion timestamps**. All **669 nonzero-generation explicit stream waits** match unique records using `(globalPid, deviceId, contextId, eventId, eventSyncId)`; 375 generation-zero waits have no valid match. Never match a gen0 wait to a later record of the same reused event ID.

Two small, actual ordering constraints in this instrumented trace:

- **45.001408–45.012512 (11.104 µs):** compute event 2146/507 completes at 45.008512; copy stream had a wait, then free, then H2D c11209 already submitted. H2D begins 4.000 µs after the event. Retirement can gate later uploads here.
- **51.714784–51.753088 (38.304 µs):** final decoder kernel ends; 27 stream-32 event completions occur before a stream-7 D2D starts. Its handoff event 2415/878 completes at 51.751520; 64 MiB D2D c13512 starts 1.568 µs later. This is a pre-submitted compute→materialization handoff, not a missing host launch.

These constraints explain some **small** intervals; they do not explain the largest queued-copy spike. Event-completion tracing can itself introduce false cross-stream dependencies, so this is not proof that equivalent gaps exist uninstrumented.

## Limitations and next decision

The capture warns about **unsupported driver 13.2 using 13.1 tracing libraries**, possibly incomplete CUDA/OSRT/NVTX events, and event tracing that can introduce false dependencies. Counts and invariants validate the exported records, not loss-free collection.

What we now know better: the whole-query input barrier, lineitem tail, actual wake-to-run delay, concrete blocking paths, timed event dependencies, and significant explicit profiler interference.

What remains unknown: exact request readiness/consumption identity, lock owners, callback-body execution, allocator-internal dependencies, and how much of each stall survives ordinary execution.

**Proposed next discussion, not executed:** obtain a supported, warmed-tracer steady-state capture before trusting large driver-side spikes; select only the minimal additional readiness markers if standard traces still cannot join file completion to its consumer/transfer. Any new capture/instrumentation needs agreement first. No optimizer or runtime redesign follows automatically from this report.
