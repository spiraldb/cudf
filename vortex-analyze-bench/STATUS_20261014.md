## Insights

1. **Zone pruning needs data order, and the harness must not supply it.** With fixtures sorted
   by date (since reverted), Q6 reached 2.4x and Q10 2.1x; on generated order the engine changes
   give 0-5%. Zone count also caps pruning: at 16Mi rows per zone SF10 orders is one zone and
   lineitem about four. Any ordering should be decided dynamically inside Vortex (at write time
   from the data, or adaptively from observed filters), never by naming tables or columns.
2. **Q5 is not prunable statically.** Its only real filter is on orders; lineitem, the bulk of
   the data, is reached only through joins. A runtime semi-join (read lineitem's join keys,
   compute matching ranges, read the rest with `row_ranges`) pruned about half of lineitem but
   made Q5 slower (12.8 -> 14.4 ms): the two reads serialize, and probing 60M keys cost ~4.5 ms.
3. **Vortex's read is copy- and orchestration-bound, not decode-bound.** In hot Q5, copying
   compressed bytes takes ~4 ms, all decode kernels ~3.5 ms, and the rest of the 8-10 ms read is
   gaps between small kernels and host syncs. Parquet spends ~15.5 ms on Snappy plus page decode.
4. **cuDF's post-read work is identical for both formats** (~5.5 ms in Q5): joins, filter,
   group-by. About half of the join time is host synchronization inside cuDF's hash join. The
   only Vortex-side lever is shrinking the inputs, e.g. by filtering inside the scan.
5. **Small chunks are expensive**: about 200 driver calls per batch on the consumer thread,
   mostly cudarc's per-access event tracking. Large (16Mi-row) chunks are strictly better
   today, so small zones and multi-column clustering are parked. Turning cudarc tracking off
   corrupted results immediately; doing explicit stream ordering safely was judged not worth
   the ~4-6% it could give at 16Mi chunks. The cudarc fork with event reuse was reverted
   (`ea96f2cef5`).
6. **Fused decode had silent fallbacks.** Dictionaries were staged into every block's shared
   memory (48 KiB cap), and dictionaries with nullable codes were never fused, which is every
   cuDF-written column. Both are fixed (`dfc666da37`, `f8fcb43a9f`): Q5 read -6%, full -3%,
   Q6 -5%. Large run-end arrays still fall back (`runend_i32_u32`, ~0.3 ms in Q5).

## Strategies to try next

Ordered by expected value for Q5, cheapest first. Measure an upper bound before building.

1. **Fix Vortex cold runs.** Shared file mappings (`7c2a45ed61`) keep pages mapped, so the
   harness cannot evict them (`Input pages remain cached after eviction`). Add a way to release
   Vortex's cached mappings that the harness calls before evicting. Then measure cold Q5 for
   both formats.
2. **Run-end decoding from global memory** in fused dispatch, mirroring the dictionary change.
3. **Hot GPU-resident compressed cache**: keep compressed segments in device memory across
   queries; removes the ~4 ms copy in hot Q5. Vortex-specific: its decode is cheap, Parquet would
   still pay ~15 ms of decompression and decode.
4. **Fill GPU idle gaps by spending CPU**: capture repeated decode plans as CUDA graphs, decode
   several columns per launch, remove remaining sync readbacks, prefetch the next batch.
5. **Exact filtering inside the scan, on the GPU**: evaluate pushed-down predicates on encoded
   data, apply the mask before export, export only selected rows. Small for Q5 (orders keeps
   ~1/7; est. 0.5-1.5 ms), large for Q6 and Q1. Prefer GPU over CPU evaluation on this machine:
   keeps compression on the wire.
6. **Projection and aggregation pushdown**: compute `l_extendedprice * (1 - l_discount)` in the
   fused decode; group on dictionary codes (Q1's 28 ms of cuDF compute).
7. **Dynamic ordering inside Vortex** for pruning: write-time choice from data, or adaptive
   reclustering from observed filters.

Each was measured as neutral, negative, or not general enough.

## Insights from this pass

1. **Nsight Systems distorts the harness's start of each read.** The harness reads tables on
   fresh `std::async` threads; under CUPTI, each new thread's first CUDA call took 0.5-3 ms
   (serialized), so the filtered tables' scans appeared to open ~3 ms late. Without the
   profiler the same window is 32-128 us (bpftrace uprobes). For profiling, a local build
   with persistent reader threads gives a faithful timeline; it was never committed.
2. **The warm read is bound by the host link.** `mapped_copy` moves pageable file pages at
   ~325 GB/s, against 340 GB/s for a pinned `cudaMemcpy`; Q5 copies ~1.2 GB in 3.85 ms of
   link time. Faithful Q5 read timeline (7.3 ms): open until 0.45 ms; copies until ~4.8 ms,
   with ~0.5 ms of gaps left after the priority change (was ~1.2 ms); ~1 ms of decode after
   the last copy; ~1 ms of harness materialization, which deep-copies every exported column
   (lineitem's four batches are concatenated: 1.6 GB device-to-device).
3. **Pageable device-to-host copies stall every thread.** The driver blocks the caller while
   holding the context lock until the stream's earlier work finishes; one FSST metadata
   readback behind queued file copies stalled all scan threads for ~2.9 ms.
4. **Compression is not the lever on this data.** The generator draws `l_discount`, `l_tax`,
   `o_totalprice`, `c_acctbal` as continuous random doubles (64 bits/row, incompressible) and
   keys are unsorted (`l_orderkey` 26 bits/row; Delta, excluded from the CUDA preset, only
   reaches 22 bits).
5. **Faster decode kernels do not show end to end yet.** Per-value FastLanes unpacking for
   u64 (and u32 above 16 bits) plus interleaved patch cursors made the fused kernel 15%
   faster on 24-bit f64 and 21% faster with 20% ALP patches, but queries were neutral
   because decode is off the critical path while copies dominate. Archived as
   `decode-parallel-unpack-interleaved-patches.patch`; worth revisiting once fewer bytes move
   (hot GPU cache, or exports without the harness copy).

## Rejected in this pass (measured, not committed)

| Experiment | Result |
|------------|--------|
| Copy kernel with one 128-thread block per SM (full link bandwidth in isolation) | neutral with or without priority streams |
| Delta in the CUDA compression preset | 2.5% fewer bytes in Q5; not worth changing the preset |
| Parallel unpack + interleaved patches (above) | kernels 15-21% faster, queries 0.99-1.02x |
| Exact filter with a host mask read back synchronously | Q6 0.62x: serialized batches |
| Exact filter decoding every column before checking for strings | Q1 0.85x: lost the direct FSST export |
| CUDA graphs, multi-column launches | not built: ~86 launches per Q5 iteration, GPU 97-99% busy while copying |
